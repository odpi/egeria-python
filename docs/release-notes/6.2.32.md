# pyegeria 6.2.32

pyegeria 6.2.32 makes these changes:
- My Profile is a production app.
- Dr.Egeria templates ship in the wheel.
- A shared step resolves an Egeria-held Dashboard Sheet for its viewer.
- Dr.Egeria's Parent ID never deletes a relationship it does not manage (ISSUE-181).
- The operations commands do what they say (ISSUE-175 to ISSUE-180).
- The stale report-spec copies and the `pyegeria/config` package are removed.

## New

- **My Profile is a production app (#580, Peter Coldicott).** Its screens, handlers, styles and assets
  move from `my_egeria/my_egeria/DemoCode/My_Profile/` into the `my_egeria` package. The app module is
  `my_egeria.my_profile`, so `my_profile` and `serve_my_profile` run it. Diagnostic logging is off. The
  UI is tidied: you can add a community, communities show persons rather than roles, screen titles are
  consistent, and the edit-profile and Tech Types navigation are fixed. The docs and tests follow the
  move. If you imported `my_egeria.DemoCode.My_Profile...`, import from `my_egeria` instead.
- **Dr.Egeria templates ship in the wheel.** The basic and advanced command templates are package data,
  under `md_processing/data/templates/{basic,advanced}/<Family>/<Command>.md`: 436 basic and 458
  advanced. A consumer (Egeria Advisor first) can read the templates that match the installed executor.
  - **Access:** `md_processing.templates` offers `list_templates`, `list_families`, `find_template`,
    `read_template`, `templates_root` and `templates_source`.
  - **Source:** `templates_source` returns `"package"` when the templates come from the wheel,
    `"checkout"` in a checkout or an editable install, and `"missing"` otherwise.
  - **Build:** `sample-data/templates` stays the only copy in git. A `build_py` hook in `setup.py` copies
    the templates into the build, and `MANIFEST.in` puts them in the sdist. The build fails if they are
    missing.
- **Resolve an Egeria-held Dashboard Sheet for its viewer.**
  `pyegeria.view.dashboard_resolver.resolve_dashboard_sheet(client, name, *, perspective=None,
  run=False)` resolves a sheet as the signed-in user sees it, so the Portal and Egeria Advisor resolve it
  the same way. It returns data only: no rendering, caching or auth.
  - **Placements:** each comes back in sheet order with its position, its kind (report, text, missing or
    restricted) and the Report and ReportSpec read as the viewer. With `run=True`, the report's result
    is included too.
  - **Restricted:** a Report in a zone the viewer can't see shows as restricted, "not visible to you",
    rather than vanishing. The writer now records each report placement's Report GUID
    (`additionalProperties.reportGUID`) so the resolver can read it by GUID. A placement written before
    this release whose link is gone can only say "missing".
  - **Already-read sheets:** `resolve_sheet` / `async_resolve_sheet` resolve a sheet the caller has
    already read.
  - **Also available as:** `pyegeria.view.dashboards.resolve_dashboard_sheet`. A viewer's sheets are
    listed by `list_dashboard_sheets_for_viewer`.

## Fixed (Dr.Egeria; ISSUE-181, HIGH)

- **Parent ID no longer deletes a relationship it does not manage.** On a command that names a `Parent ID`
  and `Parent Relationship Type Name`, Dr.Egeria read the element's relationships of that type at
  **either** end and deleted the last one that was not the named parent, before linking the parent.
  Updating a folder with a Parent ID could silently remove one of the folder's own `CollectionMembership`
  member links. Now it only adds:
  - it reads only the links with the element at the child end, paging to the end;
  - if the parent is already linked, it does nothing;
  - otherwise it links the parent and leaves any other parent link in place, naming it in the output.

  **Behaviour change:** Parent ID no longer moves an element. To move one, remove the old link explicitly
  (for example `Remove Member from Collection`).

## Fixed (operations commands; ISSUE-175 to ISSUE-180)

- **Catalog targets inherit the connector's settings.** `AutomatedCuration.add_catalog_target` /
  `update_catalog_target` (and the async forms) no longer default `permitted_sync` to BOTH_DIRECTIONS and
  `delete_method` to ARCHIVE. Unset, neither is sent: a new target inherits the connector's registered
  `permittedSynchronization`, and an update leaves both as they were. Before, every add overrode the
  connector's setting (a FROM_THIRD_PARTY connector got BOTH_DIRECTIONS targets) and every update, such
  as `tell integration-daemon update-target`, reset them. **Pass them explicitly if you relied on the old
  defaults.**
- **`tell servers start` and `stop` find the server.** Both take a required `--server` (no silent default)
  and `--organization-name`, and find the server by its resource name `<organization>.<server>`.
  `start` looked the server up by a property that finds nothing and passed the result as its name;
  `stop` looked for a qualified name equal to the bare server name, which never matches.
  `RuntimeManager.shutdown_server` gains `display_name` and `organization_name`, like
  `activate_server_with_stored_config`.
- **`tell engine-host refresh` uses its options.** `--engine-host-guid` (was the single-dash
  `-engine-host-guid`, and ignored) picks the engine host; without it the configured engine host is found by
  name, now by resource name (`refresh_gov_eng_config` gains `organization_name`). `--engine` refreshes one
  governance engine.
- **A server that cannot be found is refused.** `activate_server_with_stored_config`, `shutdown_server` and
  `refresh_gov_eng_config` raise `PyegeriaInvalidParameterException` naming the lookup when no server
  matches, instead of calling Egeria with "No elements found" as the server GUID.
- **`hey_egeria_ops show integrations targets <connector>` can be run.** It was registered as `--targets`,
  which click reads as an option.
- **Docs:** `commands/ops/README.md` describes the current commands.

## Changed

- **One copy of the generated report specs as Python code, kept current.**
  - **Before:** pyegeria shipped three copies of `dr_egeria_reports.py` (in `pyegeria/`,
    `pyegeria/config/` and `pyegeria/view/`), last generated before 6.2.28, and nothing in pyegeria
    imports them.
  - **Removed:** the two orphan copies and the `pyegeria/config/` package.
  - **Regenerated:** `pyegeria/view/dr_egeria_reports.py` now has 304 sets, the same as
    `md_processing/data/generated_format_sets.json` (the old file had 150).
  - **Kept current:** `refresh_specs` regenerates it on every run, so it can't drift again.
    `gen_report_specs --emit code` writes there by default.
  - **If you imported** `pyegeria.dr_egeria_reports` or `pyegeria.config.dr_egeria_reports`, import
    `pyegeria.view.dr_egeria_reports` instead.
