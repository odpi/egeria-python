# pyegeria 6.2.35

pyegeria 6.2.35 makes these changes:
- A tool can list the zone-restricted report specs one signed-in user may see (B6).
- A saved query is a Smart Collection when Egeria records it as one, not when a flag says so (ISSUE-184).
- `delete_saved_query` detaches a saved query's SmartQuery links before deleting it (ISSUE-183).
- A Dashboard Sheet's report tiles get their stored params: they reached the spec under the wrong names.
- A Smart Collection that Egeria has not refreshed yet reads "not refreshed yet", never 0.

## New

- **`list_visible_restricted_specs(client_as_user, folders=None)`** (`pyegeria.view.egeria_spec_cache`, B6).
  A shared report-spec cache never holds a zoned spec, so a tool that shows restricted specs reads them per
  user with this function, as that user's token: Egeria enforces the zones, so what comes back is exactly what
  that user may see. Nothing is written to any cache. Folders are walked as a sync walks them (recursive inside
  consumer folders); the result says which folders were read and why any were not.
- **`delete_saved_query(client, guid)`** (`pyegeria.view.saved_query`, ISSUE-183). Finds every Results Set
  linked to the SavedQuery by SmartQuery, from Egeria's relationships rather than the Portal's
  `additionalProperties`, detaches each through the collection-manager endpoint, then deletes the SavedQuery.
  The Results Sets are kept and named in the result (deleting one also means unlinking its members and, for a
  Smart Collection, its catalog target). A link Egeria will not detach stops the delete with the reason.
  It deletes only a SavedQuery: the element is read and its type checked first, and anything else (a GUID of a
  Report, a UserIdentity, ...) is refused with nothing deleted. The links are read page by page until Egeria
  returns an empty page; more than 2,000 is refused rather than deleted with some left behind.

## Changed

- **A Smart Collection is detected by its catalog target** (`saved_query`, ISSUE-184). A SavedQuery is
  registered as a Smart Collection, and so answered only for its stored values and labelled "kept current by
  Egeria", when a Results Set linked to it by SmartQuery is a CatalogTarget of an IntegrationConnector under the
  target name `resultsSetToMaintain` (the Smart Collections connector's declared target, Egeria #9200). That
  Results Set is the one read. Until 6.2.34 the test was the Portal's `additionalProperties.smartCollection ==
  "true"`; the flag alone no longer registers. A lookup that fails is not a registration: the query takes the
  ordinary cached path, which serves only the values its refresh recorded.

## Fixed

- **A Report's stored params reach its spec** (`dashboard_resolver`). A Report element stores its params
  camelCase in additionalProperties (`searchString`, `pageSize`, `collectionQname`, `collectionGuid`, ...) and its
  analytic params as a JSON string under `analyticParams`. `exec_report_spec` keeps only the names a spec
  declares, which are snake_case, so every stored param was dropped, and collection-scoped tiles (catalog-health's
  "Assets with No Lineage", local-dashboards-next-steps' "Tasks") failed for want of their collection. Both are
  now passed in snake_case; a key already snake_case is unchanged and wins over a converted one. The Report as
  read (`ResolvedReport.params`) keeps the stored names.
- **A Smart Collection not refreshed yet is not an empty answer** (`saved_query`). Egeria's Smart Collections
  connector stamps the Results Set's `completionTime` on each refresh, so that is the answer's "as of" (it wins
  over the Portal's refresh time). With no refresh recorded anywhere, the answer is `not_established`, "not
  refreshed yet", and the (empty) Results Set is not read as 0. A Smart Collection lookup that cannot be made is
  now said in the answer's `note`.
