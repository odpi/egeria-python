# pyegeria 6.2.40

pyegeria 6.2.40 is the release the Dr.Egeria round-trip probe built. Every property-style attribute of every
Dr.Egeria Create command was written to a scratch Egeria and read back; this release fixes what didn't come back
(F-A: creates that broke; F-B: attributes no processor applied). It also adds
`pyegeria.view.report_spec_publish`, the shared report-spec publish/withdraw helper (Stage 1a).

Checked for this release: the 3.13 micro-tests, and the round-trip probe (branch `probe/release-gate`, not part of
this release) on a PostgreSQL scratch Egeria (757a5df0) against its baseline `757a5df0.json`, with 0 regressions.

## Behaviour changes

- **"not applied" output.** An attribute Dr.Egeria can't send is no longer dropped silently. The command's
  warnings say `not applied: <attribute>: <reason>` -- a key the Egeria type doesn't declare, a value that isn't
  a whole number for an integer field, a property with no Egeria home, a relationship property with no parent link.
  Keys a type doesn't declare are no longer sent (Egeria ignored them).
- **Search Keywords are written.** After every create and update, each `Search Keywords` entry is attached as a
  SearchKeyword (its text is `displayName`). Idempotent; keywords not listed are left in place. Most commands
  never applied them before.
- **Glossary-term flags are classifications.** Is Abstract Concept, Is Activity Description (+ Term Activity
  Type), Is Context (+ Context Description / Scope) and Is Data Value now classify the term AbstractConcept,
  ActivityDescription(activityType), ContextDefinition(description, scope) and DataValueMeaning. They were sent as
  term properties, which Egeria 6 ignores. Create Question gets the term properties too.
- **Schema attribute link properties.** Element Position, Min Cardinality and Max Cardinality are sent as
  `position` / `minCardinality` / `maxCardinality` on the AttributeForSchema / NestedSchemaAttribute link to the
  parent (Parent ID + Parent Relationship Type Name), never on the attribute; with no parent link they're reported.
  Is Ordered Values is `orderedValues`. Default Value Override isn't sent (not in this Egeria's type system).
- **Refusals with a sentence.** Commands Dr.Egeria can't carry out say why and send nothing: Create Rating /
  Create Like (use **Link Element->Rating** / **Link Element->Like**), Create Data Sharing Request (a ToDo subtype in Egeria), an Asset
  Maker command with no template mapping ("not supported yet"), a To-Do / Meeting / Review for a user with no
  personal profile, a technology type or template missing on the server. Every failure now prints its exception
  type and message on one line, with Egeria's message id.
- **Opaque GUIDs.** GUIDs are treated as opaque strings. A server whose repository returns type-prefixed GUIDs
  (`Glossary-<uuid>`, Egeria's in-memory repository) no longer has nearly every Create reported as failed after
  the element was made. Where a value may be a GUID or a name, a GUID is a UUID with at most one type prefix.
- **Typed bodies.** Parent Relationship Attributes, Template Properties and (Generic) Initial Classifications are
  sent as their Egeria class (`<Type>Properties`) with only the keys it declares; sent raw they failed the whole
  create (400). Absolute/Relative Uncertainty are sent as integers (Egeria's Long).
- **Project attributes.** Project Identifier -> `identifier`; Approach / Management Style / Results Usage ->
  the ProjectClassification classification; Project Type -> its named classification. Purposes (removed) and
  Project Scope (no Egeria property) are reported. Information Supply Chain reads Purposes or Data Processing
  Purposes and now sends integrationStyle and estimatedVolumetrics.
- **Referenceable extras.** Classifications (Named DICT) are classified; Translation Details are set through
  Egeria's multi-language service (new `ClassificationExplorer.set_translation`); User Defined Status and
  Supplementary Properties are reported.
- **Commands that now run.** Create UC Server / Schema / Table Element, Create Subject Area, Create CSV File.
  Create Blog / Journal / Activity Entry now report success (they created the entry, then failed to read it back).

## Known issues

- **additionalProperties is replaced as a whole map.** On an upsert (a Create that finds its element) or any
  merge update, Egeria replaces `additionalProperties` as one value, not key by key: keys the document leaves out
  are removed. On laz a saved query's refresh keys were wiped this way. Give every key you want to keep.
- **Egeria-side gaps** (reported to the Egeria project; not fixable in pyegeria):
  - Regulation **Regulators** are not stored.
  - **Authors** are stored but lost on read for External References and Design Models (removed twice by the
    property converter).
  - Entity **Effective From / Effective To** are stored but not returned on read.
  - **Default Value Override** is declared by Egeria's SchemaAttributeProperties but not by the repository type
    definition, so Dr.Egeria doesn't send it ("not applied").
- **B5, Egeria 8840035f:** a find with `pageSize` 1 can miss an element when a same-named element was deleted
  ("No elements found" although a match exists). Use a larger page size for existence checks.

## Added

- **`pyegeria.view.report_spec_publish`** (Stage 1a): `build_publish_document`, `build_withdraw_document`,
  `check_zones`, `restricted_publish_status`, `held_in_egeria`, `document_digest` / `check_unchanged`,
  `run_document`. App-neutral (no credentials, no web or app code, no cache I/O), so the Portal and Egeria Advisor
  build and check the same Dr.Egeria documents.
- `scripts/gen_properties_class_fields.py` and the generated `md_processing_utils/properties_class_fields.py`:
  every Egeria framework Properties class, its kind and the JSON names it reads, from Egeria's Java source.

## Not in this release

The spec-metadata fixes (F-C), the MetadataExpert family, and the round-trip probe / release gate itself
(`probe/release-gate`).
