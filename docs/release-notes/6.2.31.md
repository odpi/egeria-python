# pyegeria 6.2.31

## Changed

- **The Dashboard Sheet command help says where a sheet lives.** The Dr.Egeria templates and help for
  `Create Dashboard Sheet`, `Link Report to Dashboard Sheet` and `Add Text on Dashboard Sheet` described a
  sheet as a "local pyegeria-managed record". Since 6.2.29 a sheet is held in Egeria: a Dashboard with a
  DisplayDataSchemaType, the sheet's DisplayDataContainer, and one DisplayDataField per placement. The
  local JSON store is a fallback, written alone with `--local-only` or with no Egeria connection. The
  three commands' descriptions, the `Dashboard Sheet Name` and `MD Content` attributes, and the
  regenerated templates now say so. `Create Dashboard Sheet` and `Link Report to Dashboard Sheet` had no
  description before.
- **`Create Dashboard Sheet` sets the Dashboard's owner, as `migrate` does (DB-3).** The sheet's
  Dashboard gets an Ownership classification for the user the command runs as (in the Portal, by
  default, its service user), or for the userId given in the
  new Advanced attribute `Dashboard Owner` (the same meaning as `python -m pyegeria.view.dashboards
  migrate --owner`). It is set once: a Dashboard that already has an owner keeps it, a re-run writes
  nothing, and the output says "Ownership: unchanged (already owned)" (with a note when a different
  owner was asked for). With `--local-only` or no Egeria connection nothing is set, and the output says
  "Ownership: not written (local only)". Both commands use one implementation,
  `DashboardSheetEgeriaWriter.ensure_ownership`. `Dashboard Owner` is not a column in the generated
  report specs: the owner is held in the classification, not a property.
- **"Analytic Demo - Governance Coverage" says what it counts.** Its description, and the
  `governed_coverage` registry entry, said "share of assets". It counts elements of **any type that the
  caller can see** carrying any of the five governance classifications, by a paged find: not a share of
  Assets, and not a percentage. The Overview's Governed tile is a different metric (Assets only, a native
  repository-wide count, as a share of all Assets), so the two numbers differ by definition; the spec now
  says so. The spec's label and heading are unchanged.
- **Semantic grounding counts distinct Assets.** `semantic_grounding` (and "Analytic Demo - Semantic
  Grounding") returns five new fields:
  - `groundedAssets`: the number of **distinct** Assets with a glossary term on it or on any of its
    parts (tables, columns): a SemanticAssignment on the Asset itself, or on an element anchored to it. Live, terms are assigned to
    Assets' columns, not to Assets directly, so a column's term grounds its Asset. The Asset is read
    from the `anchor` each relationship end carries, with no extra reads. A deleted (memento) element
    grounds nothing.
  - `groundedAssetTotal`: the Asset total it divides by.
  - `groundedAssetPct`: the share of Assets grounded.
  - `groundedAssetNote`: why the share is empty, when it is.
  - `groundingLinksNotOnAsset`: the links that ground no Asset (a term on a process, say), so none
    silently drop out.
  Egeria cannot count distinct relationship ends natively, so the count comes from a scan of every
  SemanticAssignment the caller can see, and the total is counted in that same (viewer) population.
  When the viewer Asset total cannot be measured (it can time out on a large catalog),
  `groundedAssetPct` is None and `groundedAssetNote` says why: never a viewer count over a repository
  total. `groundingLinks` and `groundingPct` are unchanged: the native, repository-wide link count,
  and links per hundred Assets (links, not Assets). The routine is now slower: a relationship scan
  and a viewer Asset count run beside the two native counts.
