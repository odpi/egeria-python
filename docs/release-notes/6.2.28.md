# pyegeria 6.2.28

## Fixed

- **The two unrunnable built-in report specs run again.** `Asset-Graph` named
  `ServerClient.get_asset_graph`, which no longer exists; it now calls
  `AssetCatalog.get_asset_graph_by_guid`, and its required parameter is `guid` (was `asset_guid`; the
  `hey_egeria` asset graph command passes the new name).
  `Data-Classes` named `DataDesigner.find_data_classes`, which no longer exists; it now calls
  `DataDesigner.find_data_value_specifications` restricted to the `DataClass` subtype
  (`metadata_element_subtypes=["DataClass"]`). The load-time census is now 437 specs: 376 runnable,
  61 format-only, none unrunnable (6.2.27: 374 runnable, 2 unrunnable).
- **`Asset-Graph` renders the asset graph.** It declares DICT and JSON for code, and REPORT,
  HTML and MERMAID for people. DICT is one row, the asset itself with its own fields and its graph
  fields. JSON is the full graph response. REPORT and HTML show the asset's fields with its
  asset, anchor and action graphs rendered as mermaid. MERMAID is the asset graph. The anchor
  graph's misspelt column key (`anchorMermaidGRaph`) is corrected, and an Action Graph column is
  added. TABLE, LIST, MD, FORM and ALL are not declared; asking for them is an error that names
  the declared formats, and TABLE does not fall back to the DICT row (`NO_TABLE_FALLBACK`). A table
  of a graph is its edges; that edge table is planned as its own spec in Wave 3.
- **A REPORT names a search string only when there was one.** A fetch by GUID, or a find with no
  search string, no longer says "found from the search string: `All`" (or `Members`).
- **HTML output renders markdown tables.** The HTML renderer had GFM tables switched off, so a
  markdown table in a REPORT came out as text, although the page's CSS styles tables; it is now
  a table.
- **`exec_report_spec` no longer returns `None` when a find method raises `ValueError`.** It logs
  the error and raises it, so the caller sees the words.

## Changed

- **A failed viewer count is `None`, not `0`.** `count_elements`, `count_elements_by_property` and
  the composites built on them (`counts_by_type`, `people_counts`, `usage_context_counts`) returned
  `0` in the viewer population when the query itself failed, unless `strict=True`. That read as
  "none of them". It is now `None` with an `unmeasured` note, strict or not, as a repository count
  already was. `strict` is still accepted and changes nothing.
- **Scans read every page, or report nothing.** A figure computed from a scan is only a figure
  when the scan read everything. The relationship scans and the governance, ownership and karma
  finds now page until Egeria returns an empty page (a short page is not the last page). A scan
  that cannot finish (more than `MAX_SCAN_PAGES` pages, or a server that repeats its page) is
  `None` with an `unmeasured` note, never a figure from the part it read. In 6.2.27,
  `orphan_glossary_terms` read one 500-relationship page that held 8 distinct terms, and reported
  1,053 orphan terms where all 747 relationships give 984.
- **A full page of Assets is a sample, not a count.** `stale_assets` reported `staleCount` `0`
  from a full 500-Asset page beside a not-measured `assetTotal`. It is now `None` with a note when
  the page is full. `ai_ready_assets` and `drl_readiness_gates` do the same, with `capped: true`;
  they used to report the sample's figures.
- `engagement_series`: a feedback type whose query failed is `None` in every week, and so is
  every week's `total`, where it used to read as a week of no activity.
- `governedCapped`, `ownershipCapped` and the readiness routines' `capped` are `false` whenever
  the figures were measured.

See [Counts: not measured, and whose population](../output-formats-and-report-specs.md#counts-not-measured-and-whose-population).
