# pyegeria 6.2.28

## Search and get filters: universal, checked, documented

- **Every `find_*` / `get_*` takes the standard filters as keyword arguments.** Each public
  method that sends a request body to Egeria (509 of them, sync and async) accepts `**kwargs` and
  passes them to the shared request helper. Signatures are unchanged apart from that. Methods
  that previously could not filter now can — including `DataDesigner.find_all_data_structures`
  / `find_all_data_fields`, `RuntimeManager.get_platforms_by_name` / `get_servers_by_name` and
  the other runtime lookups, `CollectionManager.get_collection_hierarchy` / `get_member_list`,
  and the get-by-GUID family (`GetFilters` now reach `GetRequestBody`; before, a filter
  keyword on a get-by-GUID was silently dropped). For example:

  ```python
  client.find_data_value_specifications("*", metadata_element_subtypes=["DataClass"])
  ```

- **Filter names are checked.** An unknown name warns with `UnknownFilterWarning` (a
  `UserWarning`, also logged at WARNING), naming the bad key and listing the valid ones, and is
  left out of the request. The valid names come from the request-body model the call sends
  (`SearchStringRequestBody`, `FilterRequestBody`, `GetRequestBody`, ...). Report specs'
  `spec_params` go through the same check, so a typo in a spec warns too.
  **A future release will raise `TypeError` instead of warning** — fix any warnings now.
- **Typed filters (PEP 692).** `SearchFilters`, `ListFilters`, `GetFilters` and `FindFilters`
  (in `pyegeria.core.request_filters`) are `TypedDict`s with a description per field. Methods
  annotate `**kwargs: Unpack[...]` so editors complete the filter names. Methods that already
  name some filters as explicit parameters keep a plain `**kwargs` (PEP 692 forbids the overlap);
  their filters still pass through and are checked.
- **Docs:** [Search and get filters](../search-and-get-filters.md) — the full tables, which
  Egeria request body each maps to, and examples.

- **One name for the type filters.** Every method now spells them `metadata_element_type`
  and `metadata_element_subtypes` (135 signatures renamed, mostly from
  `metadata_element_type_name`; also `metadata_element_sub_type`, `metadata_element_subtype`,
  `metadata_element_subtype_names`, `metadata_element_name`). The old spellings still work, with
  a `DeprecationWarning` naming the new one; giving old and new with different values raises
  `TypeError`. Report specs using the old names keep working without warnings.

- **Generic-search report specs name their type.** The 40 Dr.Egeria `*-DrE-*` specs that
  called `MetadataExpert.find_metadata_elements_with_string` with no type (Embedded-Process,
  Report, Schema-Type, the Asset Maker `*-Element-DrE-*` specs, ...) now call
  `ClassificationExplorer.find_elements_by_property_value` with their command's own type, which
  the generator takes from the command's `OM_TYPE` (`OpenMetadataRoot` for the generic Element
  command). `'*'` used to fail ("searchString is null"); it now lists the elements of that type.
  A search string used to match every type; it now matches only that type.
  - The 9 technology commands (Kafka, Postgres server/database, the Unity Catalog elements) also
    pass their `deployedImplementationType` (from the same table Dr.Egeria's create-from-template
    calls use). Egeria ANDs "technology equals" with the name search in one query, so these
    reports list exactly that technology for `'*'` and for a search string (a "Databricks Unity
    Catalog Server" is not a "Unity Catalog Server"); they show a *Deployed Implementation Type*
    column.
  - `'*'` with no type or a root type (`OpenMetadataRoot`, `Referenceable`) is refused: "give a
    search string or a narrower type" (a whole-repository listing helped run the quickstart
    platform out of heap on 2026-11-09). So `Element-DrE-*` works only with a search string.
  - `'*'` lists a type at most 100 elements per call (the caller's `page_size`, default 100);
    page on with `start_from`.
- **A misspelt report parameter warns.** `run_report` / `exec_report_spec` drop a caller's
  parameter the report does not take; they now say so with `UnknownFilterWarning`. When a
  caller's parameter collides with the spec's `spec_params`, the spec's value wins (unchanged).

### Behaviour changes: some reports now return fewer rows

These reports used to ignore part of their filter and list everything; they now return only
what they are named for. Row counts are from the quickstart demo (live reads, 2026-11-09):

| Report spec (Basic and Advanced) | Before | Now |
|---|---|---|
| `Cited-Document-DrE-*` | 87 (every external reference) | 2 |
| `Related-Media-DrE-*` | 87 | 4 |
| `External-Data-Source-DrE-*`, `External-Model-Source-DrE-*`, `External-Source-Code-DrE-*`, `External-Standard-DrE-*` | 87 each | 0 |
| `Question-DrE-*` | failed with `TypeError` (and would have listed 1000+ glossary terms) | 152 |
| `Data-Sharing-Agreement-DrE-*` (`find_collections`) | 1000+ (every collection) | 598 (Agreements classified DataSharingAgreement) |
| `Digital-Product-Catalog-DrE-*` (`find_collections`) | 1000+ (every collection) | 3 |

- **`classification_names` on a find now filters.** It is sent as
  `includeOnlyClassifiedElements` (it already meant that on a by-name get). Before, a find
  dropped it silently. So the two Dr.Egeria specs that pass `classification_names` to
  `find_collections` return fewer rows than before. `Data-Sharing-Agreement-DrE-*` now lists
  only Agreements classified DataSharingAgreement. `Digital-Product-Catalog-DrE-*` passed
  `classification_names: ["DigitalProductCatalog"]`, but `DigitalProductCatalog` is a type, not a
  classification; its Dr.Egeria `find_constraints` now uses `metadata_element_type`, so it lists
  the 3 catalogs instead of every collection. The project-family specs
  (Campaign etc.) already used `include_only_classified_elements` and are unchanged.
- **The external-reference and Question specs now return only their own type.** Their
  Dr.Egeria `find_constraints` named filters the method did not have
  (`metadata_element_types`, `classification`); they now use `metadata_element_type` and
  `include_only_classified_elements: ["Question"]`, and the report specs were regenerated.
  Dr.Egeria command processing is unchanged (it reads the singular type key the same way).
- **A hard-coded filter no longer collides with yours.** 58 call sites passed a filter such as
  `metadata_element_type` explicitly beside `**kwargs`, so passing that filter raised
  `TypeError: got multiple values` (this is why `Question-DrE-*` failed). The built-in value is
  now a default that a caller's keyword overrides.

### Other changes to check

- A filter given as `None` never overrides a method's own default.
- `MetadataExpert.find_metadata_elements` builds its default body from any `FindRequestBody`
  field given as a keyword (before: a fixed subset).
- Every built-in report spec's `spec_params` is now checked by a micro-test against the method
  it calls.
