# PY-49: audit of every shipped report spec against the Egeria 6.4 type system

**Status:** evidence only. No spec, code or Egeria change was made. Decisions Dan gave on 2026-11-22 are applied and marked **DECIDED**; everything else is a **RECOMMENDED** or **NEEDS DAN** action. The build is a separate step.

**Base:** egeria-python `odpi/main` 46b092d6 plus the PY-46 branch 13595b35 (strict validator and `KNOWN_UNKNOWN_COLUMNS`). Worktree branch `claude/py49-report-spec-audit`, docs only.

## 1. What was audited, and with what

- **Specs:** all 452 specs in `get_report_registry()` (the builtin tier is the packaged seed `pyegeria/view/seed/*.json`; the Python constants in `pyegeria/view/base_report_formats.py` and `pyegeria/view/dr_egeria_reports.py` are the seed generator's input). 133 are hand-written and 319 are auto-generated from Dr.Egeria Create commands (label contains `-DrE` or description starts `Auto-generated format for`). 26 are analytic specs with no columns of their own. 8597 columns in all.
- **Type system of record:** Egeria **6.4, build `90232870b2`** (odpi/egeria main, the #9463 merge; the same tree as head `0dbf468774`), as captured in `md_processing/md_processing_utils/properties_class_fields.py` (generated by `scripts/gen_properties_class_fields.py`: every Properties class, its kind, and the setter names Jackson binds, inherited ones included) and `pyegeria/view/egeria_relationship_fields.py` (the relationship lists on `OpenMetadataRootElement`/`AttributedMetadataElement`, generated from the same tree).
- **What I did NOT have:** the odpi/egeria Java source is not on this machine and no 6.4 platform was running, so (1) the container/containee direction of relationships and (2) `@Deprecated` markers on beans could not be read; where a finding depends on either it says so. Deprecation evidence in this report is therefore limited to what pyegeria's own code, notes and generated tables show. Behaviour on a live platform was not run.
- **How a column is classified:** a column key is looked up in this order: (a) an attribute of the target type, inherited ones included (bean field named); a formatter-derived key (`output_formatter._extract_referenceable_properties`, plus the validator's `DERIVED_KEYS`); a relationship list (`RELATIONSHIP_FIELDS`); an annotation key; for generated specs, a Create-command attribute. Keys written in camelCase are matched by their snake form (`populate_common_columns` converts the key with `to_camel_case`, which leaves a key with no underscore unchanged: `output_formatter.py:2177-2180`, `models.py:69-81`). What is left is searched for in the client code (a producer line) and in other types' beans (a subtype/other-type field). A key with no attribute, no producer and no other-type bean is dead.
- **Target types** are resolved exactly, then case-insensitively with spaces and punctuation removed. Note the validator's `egeria_type_name` is case-sensitive after removing spaces, so it misses names such as `Terms and Conditions` (section 4.3).
- **Confidence:** the pinned-spec rows (sections 2.1 and 3) and every row that carries a hand-written finding were checked by reading the cited lines. A row whose evidence is a bare `file:line` marked *pattern match* was found by a producer-line search (`key == 'x'`, `['x'] =`, `"x": value`) and the line was not read in context: treat it as a lead, not a proof. Rows marked `keep (unverified offline)` name a key whose value comes from a runtime or registry response (platform, registered services, type definitions, detail sub-tables), where no Egeria type applies and nothing could be run.

## 3. Dan's decisions applied to the pinned specs

### 3.1 Group B: containing_data_class and specializes_data_class: DECIDED, fill them in

Both relationships exist in 6.4, so these two columns are filled rather than dropped. Neither column is produced by any code today (verified: no producer line in `pyegeria/`), so they are blank in every report that carries them (Data-Classes and Data-Value-Spec).

| Column | Relationship type behind it (6.4) | Relationship list on the element | Where the client already reads it | What the fill needs |
|---|---|---|---|---|
| `containing_data_class` | **DataClassComposition** | `partOfDataClasses` (the classes this class is part of); the other end is `madeOfDataClasses`  (`egeria_relationship_fields.py:211`, `:174`) | `data_designer.py:1592-1594`, returned as `nested_data_class_*` at `:1625` (a misleading name: it holds the containing classes) | map the returned key to the column key (or rename the column); confirm direction in the Java source (not available here): the pyegeria comment says 'parent side' |
| `specializes_data_class` | **DataValueHierarchy** (there is no separate data-class specialization relationship any more: the code comment says so) | `superDataValueSpecification` (the more general specification); the other end is `subDataValueSpecifications`  (`egeria_relationship_fields.py:287`, `:284`) | `data_designer.py:1601-1604`, returned as `specialized_data_value_spec_*` at `:1637`; the key `specialized_data_class_*` (`:1629`) reads the legacy `specializedDataClasses` list, which Egeria no longer sends | map `specialized_data_value_spec_*` to the column; the legacy `specialized_data_class_*` can go |

Both relationships exist, so neither column became NEEDS DAN. On Data-Value-Spec (target DataValueSpecification, a supertype of DataClass) the columns fill only for DataClass rows.

**Flag (not a CitedDocument field): `reference_sources`** is the ExternalReference attribute `sources` (title 'Sources'), declared on ExternalReference and inherited, so it is not CitedDocument-only. **`current_version`** is titled 'Version Identifier' and is `version_identifier` (`ReferenceableProperties.versionIdentifier`); it is a Digital Product command variable that was copied across (`commands_digital_products_compact.json:2325`). CitedDocument's own field is `edition`, a different thing. Recommendation for both: rename in place and keep on External-References. That differs from the instruction to move `reference_sources …`, so it is **NEEDS DAN** to confirm.

**Actor-Roles `scope`:** `scope` is a real attribute of **ActorRole** (`ActorRoleProperties.scope`) and ActorRole also has `actorRoleGroups`. The spec's target type is `Actor Profile`, but its function `ActorManager.find_actor_roles` returns ActorRole elements (`validate.py` `FIND_ELEMENT_TYPES`). The target is what is wrong. The validator's fit check lets it pass because the pair (find_actor_roles, Actor Profile) is already in the registry (`_registry_pairs`). RECOMMENDED: fix `target_type` to ActorRole; `scope` then needs no change. Not a Group C subtype issue.

### 3.4 Group D: Governance-Controls: DECIDED, move measurement/target to GovernanceMetric; user_defined_status on both

- `measurement` and `target` are attributes of **GovernanceMetric only** (`GovernanceMetricProperties.measurement`, `.target`); GovernanceControl and GovernanceDefinition do not have them. Their lower-case titles ('measurement', 'target') show they were copied.
- **The GovernanceMetric spec already shows both:** `Governance-Metric-DrE-Advanced` and `-Basic` have `measurement` and `target`. There is **no hand-written Governance-Metrics spec** (only the two generated ones). So the move is a deletion from Governance-Controls; whether to add a hand-written Governance-Metrics spec is NEEDS DAN.
- **`user_defined_status` is not a real attribute of any element type.** The only class in the table with `userDefinedStatus` is the CollectionMembership relationship (`CollectionMembershipProperties`). The real attribute is **`userDefinedContentStatus`** (`AuthoredReferenceableProperties`), which both GovernanceControl and GovernanceMetric inherit. So your suspicion is right: it belongs on both. Today `Governance-Metric-DrE-Advanced` has `user_defined_content_status`, `Governance-Metric-DrE-Basic` and `Governance-Controls` do not.
- The same dead key `user_defined_status` is in 101 generated specs (section 6.1).
